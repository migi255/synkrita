# Synkrita's knowledge model

Synkrita keeps a source's reported values, the operator's interpretation, and permission to reuse that interpretation as separate records. This guide describes the implemented model. The [study-lineage example](STUDY_LINEAGE_EXAMPLE.md) shows how those records move through the collector and hosted MCP service.

## Record types and reuse

| Concept | Purpose, creation and storage | Trust, reuse and invalidation |
| --- | --- | --- |
| **Source declarations and capabilities** | Operator configuration grants an exact endpoint, view and operations. Discovery reads the tool catalogue and writes `declaration` records. A capability describes one tool's name, argument schema, response schema and limitations. SQLite `sources` records the local identity and view registration. [Collector](../src/synkrita/remote.py#L176) · [Capability](../src/synkrita/models.py#L17) | A declaration is a snapshot of the advertised interface. Use it to check call shape under the operator's separate grant. Re-discover when the interface or authorization changes. A listed tool, description or schema confers no permission to call it and establishes neither the meaning nor completeness of results. |
| **Evidence and observations** | A permitted invocation captures response data along with its source identity, view, operation, arguments and capture time. The collector stores a `protocol_observation` through `mcp-observe`, or `receipt` records through the typed probe path. An operator can separately ingest a bounded, eligible direct observation into the hosted store. [Observation capture](../src/synkrita/observations.py#L33) · [Hosted ingestion](../src/synkrita/pilot_storage.py#L392) | An observation establishes what was captured under the recorded contract and context. Use it as a historical premise through an authorized view. Changed schemas, missing evidence or withdrawn access can block its use. Old capture times remain old even after revalidation. Outer-schema validation of wrapped text establishes neither application success nor the inner data contract. A source response alone establishes no scientific truth. |
| **Receipts and provenance** | A receipt identifies a retained record. SQLite `records` stores an opaque ID, kind, canonical JSON and SHA-256. An evidence reference adds named JSON Pointers into that record. The resolver checks the receipt and returns its selected values with source, method, capture time and checksum. [Record store](../src/synkrita/store.py#L43) · [Evidence resolver](../src/synkrita/claims.py#L44) | Re-resolve a citation to verify its exact retained support. Missing or corrupt records, an unregistered view, schema failure or an invalid selector make that reference unusable. A local checksum detects inconsistency in stored data. It proves neither who produced the upstream response nor what the source reports today. |
| **Findings and operational knowledge** | A `Finding` records that a typed probe satisfied an input and output schema. The collector stores it as `finding` with its supporting receipt, source, view, capability, interface fingerprint, age limit, use and dependencies. [Finding](../src/synkrita/models.py#L37) · [Admission and reuse](../src/synkrita/core.py#L34) | An eligible Finding supports attempting the same capability under the matching source, view, interface and use. It can save another witness probe. The current request still invokes the source and validates its own response. An expired witness, changed binding or invalid dependency can block reuse. A Finding supplies no biological result, completeness proof or transferable method for unfamiliar sources. |
| **Claims and interpretations** | Local claim helpers append `claim` records. A reported claim selects literal response fields. An interpretation attaches supplied text to evidence or claim dependencies. A derived claim can compare reports under explicit subject, cardinality and frame assumptions. [Claim creation and replay](../src/synkrita/claims.py#L81) | Reuse is through local resolution and exact citations. Resolution rechecks view, version, evidence and dependencies, and replays supported derivation rules. Missing or unavailable support blocks resolution. Matching literals do not prove entity identity. An interpretation remains attributed reasoning, and a comparison does not adjudicate which source is correct. |
| **Candidate integration decisions** | An operator proposes a bounded statement, scope, allowed uses, expiry, evidence-age limit and semantics for each role. The candidate snapshots role-to-reference bindings with selectors and selected-value digests. It is stored in `records` as `experimental_integration_candidate`. Hosted proposals require exact approved projection references. [Candidate contract](../src/synkrita/experiments/integration_decisions.py#L30) · [Hosted proposal](../src/synkrita/pilot_storage.py#L446) | A pending candidate is input to review. Its ID cannot be read as an approved decision. A change in context, retrieval binding, semantics or material evidence calls for reassessment. Role names and semantic labels are operator-supplied and confer no authority to apply the statement elsewhere. |
| **Reviews, qualification and revocation** | The operator registers a reviewer key and grant. Hosted activation verifies an Ed25519 approval over the exact candidate digest and use. It stores review and decision records, a signed attestation and a scoped activation in `hosted_decisions`. [Activation and revocation](../src/synkrita/pilot_storage.py#L415) · [Applicability checks](../src/synkrita/experiments/integration_decisions.py#L115) | A read by decision ID rechecks the stored binding, signature, current reviewer grant, historical premises and freshness of the bound observations. Decision revocation, reviewer disablement, source-policy withdrawal or expiry can stop serving it while preserving history. Qualification establishes eligibility under the reviewed scope and use. A signature authenticates the attestation, and the organization is responsible for reviewer independence. Qualification proves neither scientific truth nor live upstream validity. |
| **Private investigations and shared approved knowledge** | Local operators create owner-bound questions and notes in `hosted_investigations`. Shared evidence is a separate operator-approved scalar projection indexed by `hosted_public` and `hosted_source_policies`. Active decisions have their own approval path. [Owner lookup](../src/synkrita/pilot_storage.py#L270) · [Publication policy](../src/synkrita/pilot_storage.py#L294) · [Hosted tools](../src/synkrita/remote_server.py#L370) | Authorized accounts can read published evidence and qualified decisions by supplied ID. Only the owner can read their investigation. Missing and foreign investigations return the same unavailable result. Account suspension or credential revocation can block reads. Source withdrawal can block shared citations and dependent decisions. A private note or a successful read never promotes content into the shared catalogue. |

The `experimental_integration_*` record names are historical. The hosted application uses this decision code in its signed approval path. A collector's `public` view is a source scope. Serving it to researchers additionally requires explicit hosted publication.

## How the records fit together

In the synthetic lineage example, a specimen record and an assay record both report aliquot `ALIQUOT_001` for release `v1`. The declaration describes the lookup. A Finding supports a later lookup under the same capability, and each current response gets its own receipt. The operator projects only the record ID, aliquot ID and release, preserving citations to both reports. A local reported claim could quote either report. The operator supplies the interpretation that this pairing can be used to trace the assay's sample lineage within that release. A scoped signed approval qualifies that decision, and a second enrolled account retrieves the same decision and citations without reading the first researcher's notes.

Hosted reads use exact IDs and the activation's stored binding. A researcher cannot supply new context or evidence to that endpoint. The application has no automatic search for applicable decisions, structural transfer to unfamiliar investigations, or automatic promotion of claims. Such capabilities would require separate evaluation. See [scientific source configuration](REMOTE_MCP_QUALIFICATION.md) for collector contracts and [self-hosting](SELF_HOSTING.md#operator-package-and-acceptance) for deployment acceptance.
